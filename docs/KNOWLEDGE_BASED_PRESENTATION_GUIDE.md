## ۰. روش کار «فرمول cmd»

همهٔ نمایش‌ها با **یک دستور** اجرا می‌شوند. فقط داخل پوشهٔ پروژه یک CMD باز کن (Win+R ← `cmd`) و دستور را بنویس:

```cmd
cd /d C:\مسیر\پروژه\DOF-Digital-Oil-Field
scripts\demo\demo.cmd fullstack
```

| درخواست داور | فرمول (یک خط) |
|---|---|
| «فول‌استک را نشان بده» | `scripts\demo\demo.cmd fullstack` |
| «فقط Grafana» | `scripts\demo\demo.cmd grafana` |
| «فقط Prometheus» | `scripts\demo\demo.cmd prometheus` |
| «فقط Kafka» | `scripts\demo\demo.cmd kafka` |
| «فایل اکسل داده» | `scripts\demo\demo.cmd excel` |
| «کنسول‌هایی که داشبورد را زنده اجرا می‌کنند» | `scripts\demo\demo.cmd live` |
| «کد فرانت‌اند» | `scripts\demo\demo.cmd frontend-code` |
| «کد بک‌اند» | `scripts\demo\demo.cmd backend-code` |
| «CI/CD چگونه کار می‌کند؟» | `scripts\demo\demo.cmd cicd` |
| «تست‌ها را اجرا کن» | `scripts\demo\demo.cmd tests` |
| «سلامت سرویس‌ها» | `scripts\demo\demo.cmd health` |
| پایان جلسه | `scripts\demo\demo.cmd stop` |
| لیست همهٔ فرمول‌ها | `scripts\demo\demo.cmd help` |

> ⚠️ فایل `scripts/demo/demo.cmd` روی ویندوز نوشته شده ولی در محیط توسعهٔ ما (لینوکس) اجرا نشده است. **حتماً یک بار قبل از جلسه همهٔ فرمول‌ها را روی لپ‌تاپ ارائه تمرین کن.**

### پیش‌نیازها (یک بار، شب قبل از جلسه)
1. Docker Desktop (روشن و Running)، Python 3.11، Node.js 18+، Git، VS Code (دستور `code`)، Microsoft Excel.
2. `git clone https://github.com/parsasohrab1/DOF-Digital-Oil-Field` و ورود به پوشه.
3. `pip install -r requirements.txt` و `cd frontend\web && npm install`.
4. یک بار `demo fullstack` را اجرا کن تا ایمیج‌های Docker دانلود شوند (اینترنت لازم است؛ در جلسه اینترنت نداری!).
5. دستور `demo tests` را بزن و مطمئن شو سبز است.

## ۱. محصول در یک پاراگراف (حفظ کن)

**DOF (Digital Oil Field / «هوشمندسازی میادین»)** یک پلتفرم نرم‌افزاری هوشمند است که داده‌های حسگرهای چاه‌های نفتی (فشار، دما، دبی و …) را جمع می‌کند، کیفیت آن را کنترل می‌کند، در پایگاه داده سری‌زمانی ذخیره می‌کند، با مدل‌های یادگیری ماشین ناهنجاری و خرابی را پیش‌بینی می‌کند، هشدار می‌دهد و در یک داشبورد فارسی نمایش می‌دهد. نمونهٔ نمایشی ما بر پایهٔ **میدان دهلران** است.

### واژه‌نامهٔ آماتور
| واژه | یعنی چه | مثال ساده |
|---|---|---|
| Frontend | صفحهٔ وبی که کاربر می‌بیند | داشبورد |
| Backend | موتور پشت صحنه | ۱۴ سرویس پایتونی |
| API Gateway | درِ ورودی واحد همهٔ درخواست‌ها (پورت ۸۰۰۰) | نگهبان ساختمان |
| Docker | جعبه‌هایی که هر برنامه را با همهٔ وابستگی‌هایش اجرا می‌کند | کانتینر حمل‌ونقل |
| Kafka | صف پیام پرسرعت برای جریان داده | سیستم پست بین سرویس‌ها |
| TimescaleDB | پایگاه دادهٔ مخصوص داده‌های زمانی | دفتر ثبت لحظه‌ای حسگرها |
| Prometheus | جمع‌کنندهٔ شاخص‌های سلامت سرویس‌ها | دماسنج سرویس‌ها |
| Grafana | نمودارهای زندهٔ Prometheus | مانیتور اتاق کنترل |
| CI/CD | ربات خودکار که با هر تغییر کد، تست و بیلد می‌کند | بازرس کیفیت خط تولید |
| SCADA/OPC-UA/Modbus | پروتکل‌های صنعتی اتصال به تجهیزات | زبان تجهیزات میدان |

## ۲. وضعیت صادقانه محصول (قبل از جلسه بخوان)

### ✅ با شواهد اجرایی تأیید شده (در محیط توسعه، با sqlite/Redis بدون Docker)
- بیلد فرانت‌اند (`tsc` + `vite build`) موفق است (۵ خطای TypeScript رفع شد).
- **۲۰۶ تست بک‌اند پاس شد** (پوشش کد ماژول‌های امنیتی ۹۹٪).
- `black` و `flake8` تمیز هستند.
- ۱۳ سرویس بک‌اند اجرا شدند و `/health` همه ۲۰۰ برگرداند.
- مسیر دادهٔ کامل از طریق Gateway: ورود (JWT) ← ثبت تگ ← ثبت داده (`/ingest`) ← ذخیره ← خواندن (`/sensor-data`) ← ثبت فرمان کنترلی (وضعیت `pending`) کار می‌کند.

### 🔧 مشکلات قطعی که پیدا و رفع شد
| مشکل | علت ریشه‌ای | اصلاح |
|---|---|---|
| HTTP 500 روی هشدار/فرمان/تگ | جدول‌ها هرگز ساخته نمی‌شدند (در compose مرحلهٔ migration/init_db نبود) | `ensure_dev_tables()` در استارت سرویس‌ها (فقط development) |
| HTTP 500 روی `/health` ingestion | متغیر `mqtt_client` تعریف نشده بود (NameError) | تعریف مقدار پیش‌فرض |
| HTTP 500 روی `/api/digital-twin/wells` | `from models import` اشتباه | `from shared.models import` |
| 404 روی `/api/data-ingestion/sensor-data` | endpoint وجود نداشت ولی فرانت‌اند و Gateway صدایش می‌زدند | افزودن `GET /sensor-data` + تست |
| اختلاف پورت ۱۸۰۰۰ و ۸۰۰۰ | Vite/اسکریپت‌ها ۱۸۰۰۰، Docker/Dockerfile ۸۰۰۰ | همه ۸۰۰۰؛ با `VITE_API_PROXY_TARGET` قابل تغییر |
| Kafka در Docker قابل اتصال نبود | broker فقط `localhost:9092` معرفی می‌کرد؛ کانتینرها به `kafka:9092` وصل می‌شدند | دو listener: داخلی `kafka:29092`، بیرونی `localhost:9092` |
| نصب وابستگی‌ها شکست می‌خورد | تعارض `pydantic 2.5.0` با `2.5.2` | یکسان‌سازی |
| Smoke Tests روزانهٔ CI قرمز | pytest نصب نمی‌شد + آستانهٔ پوشش ۸۵٪ روی زیرمجموعهٔ تست‌ها | نصب pytest و `--no-cov` |
| خطای psycopg2 در تست | ناسازگاری با Python 3.13؛ با **Python 3.11** (نسخهٔ CI) مشکلی نیست | استفاده از 3.11 |

### ❓ هنوز تأیید نشده (آن را «انجام‌شده» معرفی نکن)
1. **اجرای Docker Compose کامل** (Kafka, TimescaleDB, Grafana, Prometheus) — در محیط ما Docker نبود. فقط پیکربندی اصلاح شد؛ باید روی لپ‌تاپ خودت یک بار اجرا شود.
2. **اتصال Prometheus به سرویس‌ها**: `/metrics` در ۶ سرویس بررسی و ۲۰۰ بود؛ اسکرپ واقعی داخل Prometheus و داشبورد Grafana (`ogim-apm-overview.json`) دیده نشده. سرویس‌های `data-variables`، `storage-optimization`، `remote-operations` در `prometheus.yml` نیستند.
3. **جریان واقعی Kafka** (تولید/مصرف پیام) و مصرف‌کننده‌ها (Flink jobs) اجرا نشده‌اند.
4. **CI/CD**: وضعیت اجرای GitHub Actions: Smoke Tests روزانه قرمز بود (علتش رفع شد؛ باید بعد از merge سبز شدنش دیده شود). `ML Retraining` هم قرمز است؛ به secretهای `DATABASE_URL` و `MLFLOW_TRACKING_URI` وابسته است و بررسی نشده. `ci-cd.yml` از اکشن‌های قدیمی (v3) استفاده می‌کند.
5. **`/api/digital-twin/wells`** از TimescaleDB لیست چاه را می‌خواند ولی جدول `tags` در PostgreSQL است؛ در استقرار واقعی احتمالاً همیشه لیست پیش‌فرض (PROD-001…) را می‌دهد. بررسی نشده.
6. مسیرهای `/api/maintenance/*` و `/api/scada/*` که فرانت‌اند صدا می‌زند، در Gateway سرویسی ندارند (۴۰۴). صفحات مربوط احتمالاً با داده محلی کار می‌کنند.
7. `/api/storage-optimization/*` به TimescaleDB واقعی نیاز دارد؛ روی sqlite خطا می‌دهد (انتظار می‌رود) و روی Timescale تست نشده.
8. اتصال به **SCADA/OPC-UA/PLC واقعی**، پیامک واقعی، ERP واقعی: فقط کد و شبیه‌ساز؛ هیچ تجهیز واقعی در تست نبود.
9. فرمان‌های کنترلی: ثبت و صف شدن تأیید شد؛ **اجرای واقعی روی تجهیز، تأیید دومرحله‌ای و انتشار به Kafka** تأیید نشده.

### 🎭 داده واقعی یا شبیه‌سازی؟ (داوران حتماً می‌پرسند)
| بخش | وضعیت |
|---|---|
| `data/*_sample_1week.csv` | **شبیه‌سازی‌شده** با `scripts/generate_sample_data.py` (۴ چاه، ۱ هفته، ۱ دقیقه). در گیت نیست؛ با `demo excel` تولید می‌شود. |
| `data/variables_list.csv` | فهرست ۶۵+ متغیر میدانی با واحد/بازه (مرجع مهندسی) |
| داشبورد در حالت آفلاین (`VITE_OFFLINE_LIVE=true`) | **مدل محلی شبیه‌سازی دهلران** (`source: local-dehloran-model`) — برچسب «زنده آفلاین» در بالای صفحه |
| داشبورد با بک‌اند | داده از مسیر `/ingest` ← TimescaleDB ← `/sensor-data` |
| داده واقعی میدان | **در این نسخه وجود ندارد.** جمله‌ی صادقانه: «معماری آمادهٔ اتصال به داده واقعی است؛ اعتبارسنجی با داده واقعی مرحلهٔ پایلوت است.» |

## ۳. سناریوی نمایش گام‌به‌گام

برای هر مورد: **فرمول ← چه می‌بینی ← چه بگویی ← اگر خراب شد**.

### ۳.۱ نحوهٔ کار CI/CD
- فرمول: `scripts\demo\demo.cmd cicd`
- می‌بینی: فایل `.github/workflows/ci-cd.yml` و صفحهٔ Actions گیت‌هاب.
- بگو: «با هر Push یا Pull Request، یک ربات روی سرور گیت‌هاب: ۱) کد را می‌گیرد، ۲) وابستگی‌ها را نصب می‌کند، ۳) سبک کد (black/flake8) و تست‌ها را اجرا می‌کند، ۴) فرانت‌اند را بیلد می‌کند. اگر چیزی خراب باشد، قرمز می‌شود و کد وارد شاخهٔ اصلی نمی‌شود. ما ۴ workflow داریم: `backend-ci`، `ci-cd`، `smoke-tests` (روزانه ۰۶:۰۰ UTC) و `ml-retrain` (بازآموزی هفتگی مدل).»
- صادقانه: «Smoke Tests چند روز قرمز بود؛ علتش (نصب نشدن pytest و آستانهٔ پوشش) پیدا و اصلاح شد.» (قبل از جلسه صفحهٔ Actions را ببین؛ اگر هنوز قرمز است همین را بگو و دروغ نگو.)

- فرمول: `scripts\demo\demo.cmd fullstack`

- بگو: «معماری میکروسرویس است: هر قابلیت (احراز هویت، ورود داده، هشدار، فرمان، دوقلوی دیجیتال، گزارش، ML …) یک سرویس مستقل است و همه از یک Gateway می‌گذرند.»

## ۴. سؤالات احتمالی داوران و پاسخ‌های پیشنهادی

> (جاهای `[...]` را با اطلاعات واقعی شرکتتان پر کن. سؤالات خودت را در بخش ۵ اضافه کن.)

### الف) ماهیت دانش‌بنیان و نوآوری
1. **محصول دقیقاً چه مشکلی را حل می‌کند؟** — اتصال داده‌های پراکندهٔ حسگرهای چاه، کنترل کیفیت داده، تشخیص زودهنگام خرابی/ناهنجاری و تصمیم‌یاری، در یک پلتفرم فارسی و بومی.
2. **نوآوری فناورانه چیست؟** — ترکیب خط لوله جریان داده (Kafka) + دوقلوی دیجیتال + مدل‌های ML (پیش‌بینی LSTM، RUL، یادگیری فدرال) + کارکرد در شرایط قطع ارتباط (بافر آفلاین) + رابط فارسی. فقط مواردی را برجسته کن که کدش را نشان می‌دهی.
3. **تفاوت با نمونه‌های خارجی (AVEVA, Schlumberger, Honeywell)؟** — بومی بودن، عدم وابستگی به تحریم/مجوز، هزینهٔ کمتر، سفارشی‌سازی برای میدان‌های ایران، پشتیبانی فارسی. (ادعای برتری فنی بدون آزمون نکن.)
4. **سطح آمادگی فناوری (TRL) چند است؟** — صادقانه: نمونهٔ اولیهٔ عملیاتی در محیط آزمایشگاهی (TRL ۴–۵)، با داده شبیه‌سازی‌شده؛ پایلوت میدانی مرحلهٔ بعد.
5. **چه بخشی را خودتان توسعه داده‌اید و چه بخشی متن‌باز است؟** — منطق کسب‌وکار، سرویس‌ها و داشبورد توسعهٔ خودمان؛ زیرساخت‌ها (Kafka, PostgreSQL, TimescaleDB, Grafana, Prometheus, React, FastAPI) متن‌باز استاندارد. فهرست وابستگی‌ها در `requirements.txt` و `package.json`.
6. **مالکیت فکری؟** — کد منبع متعلق به شرکت؛ [ثبت اختراع/نرم‌افزار/کپی‌رایت: وضعیت را بنویس]. مجوز کتابخانه‌های متن‌باز بررسی شده است [تأیید کنید].
7. **ریسک فنی کجاست؟** — اتصال به تجهیزات واقعی و کیفیت داده میدانی؛ مدل‌ها نیاز به داده واقعی برای واسنجی دارند.

### ب) داده
8. **داده از کجا می‌آید؟** — OPC-UA، Modbus، MQTT، LoRaWAN و REST (`/ingest`)؛ در نسخهٔ نمایشی شبیه‌ساز.
9. **داده واقعی دارید؟** — نه در این نسخه (بخش «داده واقعی یا شبیه‌سازی»). گفتن صریح، اعتبار می‌سازد.
10. **کیفیت داده چگونه کنترل می‌شود؟** — اعتبارسنجی بازه (min/max هر تگ)، DVR (اعتبارسنجی و آشتی داده)، تشخیص outlier، سلامت و رانش حسگر.
11. **اگر ارتباط قطع شود؟** — بافر آفلاین (`offline_buffer`) و تلاش مجدد؛ داشبورد در حالت آفلاین هم کار می‌کند.
12. **حجم داده و مقیاس؟** — TimescaleDB با hypertable و فشرده‌سازی؛ پیکربندی چندگره (`docs/TIMESCALEDB_MULTINODE.md`). عدد کارایی بدون آزمون بار نگو؛ آزمون بار انجام نشده.
13. **داده کجا ذخیره می‌شود و مالک کیست؟** — روی سرور خود مشتری (on-premise)؛ بدون ارسال به خارج.

### ج) هوش مصنوعی
14. **چه مدل‌هایی دارید؟ دقتشان؟** — مدل‌های ناهنجاری، پیش‌بینی LSTM، RUL؛ دقت روی داده شبیه‌سازی‌شده معنی میدانی ندارد و ادعای عدد دقت نکن مگر گزارش آموزش را داشته باشی (`scripts/train_models.py`، MLflow).
15. **چگونه از «رانش مدل» مطلع می‌شوید؟** — endpointهای drift، A/B test و مقایسهٔ نسخه‌ها در `ml-inference-service`.
16. **یادگیری فدرال یعنی چه؟** — هر میدان مدل را روی داده خودش آموزش می‌دهد و فقط وزن‌ها ادغام می‌شوند؛ داده از میدان خارج نمی‌شود.
17. **توضیح‌پذیری؟** — RCA هشدارها و همبستگی هشدارها در alert-service.

### د) امنیت (صنعت نفت: حساس)
18. **احراز هویت و دسترسی؟** — JWT، نقش‌ها (system_admin, data_engineer, field_operator, viewer)، محدودیت نقش برای هر سرویس در Gateway.
19. **فرمان کنترلی خطرناک؟** — فرمان ابتدا `pending` است، نیاز به تأیید دارد، ثبت ممیزی (audit log) و در نسخهٔ فعلی اجرای واقعی روی تجهیز تأیید نشده.
20. **محافظت در برابر حمله؟** — Rate limit، فیلتر ورودی (injection)، تشخیص تهدید + SIEM، Zero-Trust، mTLS اختیاری.
21. **رمز پیش‌فرض و ورود خودکار؟** — فقط دمو؛ در production سیستم با رمز placeholder بالا نمی‌آید.
22. **استانداردها؟** — [IEC 62443 / ISO 27001: وضعیت انطباق را صادقانه بنویس؛ اگر گواهی ندارید بگو «طراحی بر اساس اصول …، ممیزی رسمی در برنامه»].
23. **بلاکچین؟** — صفحهٔ «ثبت بلاکچین» برای ثبت غیرقابل‌تغییر ممیزی است؛ وضعیت واقعی پیاده‌سازی را قبل از جلسه در کد چک کن.

### هـ) معماری و کیفیت
24. **چرا میکروسرویس؟** — توسعه/مقیاس مستقل؛ هزینه: پیچیدگی عملیاتی.
25. **چگونه از کیفیت مطمئن می‌شوید؟** — ۲۰۶ تست خودکار، black/flake8، CI روی هر PR، آستانهٔ پوشش ۸۵٪ روی ماژول‌های امنیتی.
26. **چه چیزی تست نشده؟** — تست بار، تست با تجهیز واقعی، Docker Compose کامل در CI. (بگو؛ نقطهٔ ضعف پنهان‌شده بدتر از نقطهٔ ضعف اعلام‌شده است.)
27. **مشاهده‌پذیری؟** — Prometheus (شاخص)، Grafana (نمودار)، OpenTelemetry + Tempo (ردیابی)، لاگ JSON ساخت‌یافته.
28. **پشتیبان‌گیری و بازیابی؟** — [مستندات `docs/` را مرور کن؛ اگر اجرا نشده، «در برنامه» بگو].
29. **استقرار در محیط واقعی؟** — Docker Compose برای توسعه، مانیفست Kubernetes در `infrastructure/kubernetes`، اسکریپت `deploy_production.sh`. استقرار تولیدی اجرا نشده.

### و) بازار و کسب‌وکار
30. **مشتری هدف؟** — شرکت‌های بهره‌بردار میادین نفت و گاز (مثلاً مناطق نفتخیز)، پیمانکاران EPC/نگهداری.
31. **مدل درآمدی؟** — [لایسنس سالانه / SaaS on-premise / پشتیبانی / سفارشی‌سازی].
32. **مشتری یا قرارداد/تفاهم‌نامه دارید؟** — [بنویس؛ بدون مدرک ادعا نکن].
33. **رقبای داخلی؟** — [فهرست رقبا و تمایز].
34. **اندازهٔ بازار؟** — [عدد با منبع].
35. **نقشهٔ راه ۱۲ ماه؟** — پایلوت میدانی، اتصال به SCADA واقعی، آزمون بار، گواهی امنیتی، واسنجی مدل با داده واقعی.

### ز) تیم و شرکت
36. **تیم فنی و تخصص‌ها؟** — [نفرات، مدرک، سابقه].
37. **سرمایه و منابع مالی؟** — [ارقام].
38. **چرا این محصول «دانش‌بنیان» است؟** — بخش عمدهٔ ارزش افزوده از دانش فنی (الگوریتم‌ها، معماری) است نه خرید/فروش کالا؛ سهم پژوهش‌وتوسعه [درصد].

### ح) سؤال‌های «تله» (آماده باش)
40. «این نمودارها واقعی‌اند؟» ← بخش داده شبیه‌سازی‌شده؛ همیشه راست بگو.
